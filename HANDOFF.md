# Handoff

For a developer picking this repository up cold. It answers four questions in
order: what this is, what runs today, what is built but does not run, and where
you would start if the job is to make it run.

`README.md` describes the architecture. This file describes the build.

---

## 1. What this is

Agent OS is a constitutionally-governed multi-agent runtime. Twenty-six modules
— eleven of them "Gateways" — that let autonomous agents plan, decide, act
through tools, and learn, under enforced boundaries (tenant, scope, authority,
confidence, budget, temporal), human-authority decision gating, an immutable
audit journal, and a kill switch.

It was built from a ratified specification rather than from a backlog. Seven
documents in `ARCHITECTURE_BASELINE/` are treated as immutable, and every
module, interface and test traces to a section of them. Where the specification
was silent or self-contradictory, work stopped and escalated rather than
guessing — see `docs/rulings/CIR-001.md` for the one time that happened and how
it was resolved.

That constraint explains most of what is unusual about this codebase, including
the gap described in section 3.

## 2. What runs today

**One thing: Post Studio.** It is the content agent — the user writes what they
did that week, it drafts a LinkedIn post, a newsletter issue and a Dev.to
article from the same facts, and a human approves each draft before anything
leaves the machine.

```bash
python scripts/serve.py          # http://127.0.0.1:7860
```

Needs `GROQ_API_KEY` in `.env` (copy `.env.example`). Everything persists to
`agent.db` beside the repo. See `START_HERE.md` for the end-user walkthrough
and `docs/HOSTING.md` for deploying it.

It is worth reading `services/content_agent/` first even though it is the least
architecturally interesting module, because it is the only one where you can
watch the ideas do something.

Other entry points, all local scripts rather than services:

| Script | What it does |
|---|---|
| `scripts/serve.py` | Post Studio |
| `scripts/publish_due.py` | Posts approved-and-scheduled drafts; meant for cron / Task Scheduler |
| `scripts/linkedin_post.py` | LinkedIn OAuth and posting |
| `scripts/import_drafts.py` | Imports markdown drafts into the studio |
| `scripts/publish_voice.py` | Builds a voice persona from rated samples |

## 3. What is built but does not run

**The other twenty-five modules are libraries with tests. Nothing runs them.**

There is no process that starts `agent_runtime`. There is no socket behind
`api_gateway`. There is no broker behind `event_bus`, and no database behind the
repositories except SQLite and an in-memory adapter. The whole system is
in-process.

This is deliberate and the code says so. From
`services/api_gateway/api_gateway/ingress.py`:

> The Gateway is deliberately transport-agnostic. `Request` and `Response` are
> plain records rather than a web framework's types... What is implemented here
> is every ingress *semantic* the constitution requires; what is missing is the
> socket.

So what you have is a complete, rigorously tested **engine** that has never been
bolted into a car. Every rule about how a request must be authorized, how a
decision must be gated, how an event must be admitted and replayed, how a budget
must be enforced — implemented and proven by test. What is absent is transport,
scheduling, deployment, and durable multi-process state.

**If the job is "give it a driving force," that gap is the job.** Section 6 says
where to start.

### The 35 deviations

`docs/appendix_f_traceability.md` records 35 rules that are binding and not
satisfied. They are the technology mandates from specification document 03:
FastAPI, PostgreSQL, Temporal. This build uses none of them.

That is not an oversight and not a block. It is recorded in its own category
precisely so it cannot be mistaken for "nobody checked." A developer building
the runtime is, in large part, closing these 35.

## 4. Reading order

Roughly an afternoon to be genuinely oriented.

1. **`IMPLEMENTATION_JOURNAL.md`** — start here, not with the code. Twenty-one
   dated entries recording what was built, what broke, and why decisions went
   the way they did. The "Issues Encountered" and "Open Items" sections are the
   honest parts.
2. **`docs/appendix_f_traceability.md`** — 464 rules extracted from the
   specification, each mapped to the test that proves it or marked uncovered
   with a reason. Generated by `tests/conformance/matrix.py`, never hand-edited,
   so it cannot drift from the code. This is the fastest way to answer "is
   rule X actually enforced?"
3. **`libs/kernel/`** — the substrate every module builds on: identity,
   lifecycle, boundaries, the audit journal, failure classification, panic.
4. **`services/decision_gateway/`** — the human-authority gating (Class A–D).
   The most load-bearing idea in the system.
5. **`docs/modules/`** — nineteen per-module design docs.
6. **`services/content_agent/`** — the one module that does something a person
   notices.

`ARCHITECTURE_BASELINE/` is the source of truth but it is long. Read it when a
specific question sends you there, not front to back.

## 5. Running it

Python 3.11 (3.11.15 is what this was last verified on). No package install
step — `conftest.py` at the repository root puts every lib and service on
`sys.path`, which is what `poetry install` with workspace dependencies would do
once each package has its own virtualenv.

```bash
pip install pytest pytest-cov pydantic ruff==0.16.1 mypy==1.10.0 bandit==1.7.9
```

`pydantic` is a genuine runtime dependency of `libs/kernel` and `libs/core`. The
rest are development tools. Post Studio on its own is standard library only,
which is why its Dockerfile installs nothing.

### The gates, exactly as CI runs them

```bash
ruff check libs services tests
ruff format --check libs services tests
mypy .
python -m pytest libs/ services/ tests/ -q --cov=libs --cov=services --cov-fail-under=90
bandit -r libs services --exclude "*/tests/*"
```

Those five commands are four of the five CI jobs (`lint` runs the first two).
The fifth, `workflow-definitions`, covers the TypeScript half of the Temporal
workflow definitions:

```bash
cd services/workflow_engine/workflow_definitions
npm ci && npm run build && npm test
```

Tool versions are pinned to match `.pre-commit-config.yaml` exactly, so the hook
and the gate never disagree. Run `pre-commit install` before your first commit.

### Things that will trip you up

- **`mypy .` reports errors locally.** CI pins mypy 1.10.0; a newer local mypy
  flags untyped-decorator issues in test files that the pinned version does not.
  Match the pin before concluding you broke something.
- **`ruff check .` fails; `ruff check libs services tests` passes.** CI only
  gates the three source trees. `.claude/` is not linted.
- **Conformance registers are generated.** If you add or remove a module,
  introspected counts change and register tests fail. Regenerate with
  `python tests/conformance/generate.py` — never hand-edit the output.
- **Post Studio caches `page.html` at import.** Editing the page and refreshing
  the browser shows the old UI. Restart the server.

## 6. If the job is to build the runtime

In dependency order, smallest useful increment first.

1. **Put a socket behind `api_gateway`.** `ingress.py` already defines every
   request, response and error-envelope semantic the specification requires.
   A web framework has to adapt to those records rather than replace them.
   Everything downstream is already reachable in-process, so this alone gives
   you a system you can talk to.
2. **Give `persistence` a real adapter.** The ports-and-adapters seam is already
   there — `Repository` is a Protocol with in-memory and SQLite implementations.
   A PostgreSQL adapter is a third implementation, not a refactor.
3. **Put a broker behind `event_bus`.** Admission, backpressure, causality,
   replay and delivery semantics are implemented; the transport is not.
4. **Host `agent_runtime` in a process** with a real scheduler.
5. **Then Temporal**, which is where the TypeScript workflow definitions stop
   being a compile-checked artifact and start orchestrating.

Two warnings, both learned the hard way and both recorded in the journal:

- **The human approval boundary is a design property, not a feature.** No path
  from draft to publication may bypass it. Several tests exist only to assert
  that no such path was added. If a change makes one of those tests fail, the
  change is wrong.
- **Do not resolve a specification conflict by implementation fiat.** Build Spec
  Section 6 rule 9 requires a governance ruling. `docs/rulings/CIR-001.md` shows
  what one looks like and how narrowly its scope was held — fifteen tests stand
  between "this authorized construction" and "this relaxed the constraints."

## 7. Known open items

From the journal's most recent entries, unchanged:

- **128 uncovered rules** in Appendix F, 67 of them genuinely principle-level
  in specification document 01.
- **35 recorded deviations** from document 03's technology mandates. Closing
  them is section 6, not a bookkeeping pass.
- **No experiment runtime in `evolution_gateway`.** Bounds, scope and rollback
  plans are validated at framing, but nothing runs an experiment.
- **Standing orders are duplicated** across `decision_gateway` and
  `human_interface`.
- **Definition of Done is environmental, not architectural.** Poetry-managed
  reproducible builds and `docker compose up` from a clean clone are both
  Section 39 criteria that have not been met. Nothing in the repository blocks
  either.

No module is claimed to be at full Definition of Done, and the journal says so
rather than rounding up.
