# CIR-001 — Governance Ruling

| Field | Value |
|---|---|
| **Interpretation** | CIR-001 — Technology naming conflict between `03_TECH_STACK` and `17`, `18`, `19` |
| **Authority required** | G3 or G4 |
| **Authority exercised** | **G4 — Human Sovereign** |
| **Ruled** | 2026-08-24 |
| **Status** | **Resolved** |

## The ambiguity, as 21A §3 states it

`19` rule 22 provides: "No constitutional document, policy, or governance
artifact may reference a specific implementation technology, provider, or
substrate operator." `17` rule 21 and `18` rule 18 state materially equivalent
prohibitions.

`03_TECH_STACK` is a ratified constitutional document classified
"Implementation Specification — Binding on All Implementation Work," and it
names approximately fifty technologies as mandatory.

Under a literal reading, a ratified constitutional document violates three
non-violable rules.

## The ruling

Of the four candidate readings 21A §3 places before the resolving authority,
this ruling adopts the first:

> **The prohibition governs capability abstractions and governance artifacts.
> `03`'s classification as an Implementation Specification distinguishes it
> from the constitutional documents the rule addresses.**

### What this means in practice

**Capability abstractions remain provider-neutral, absolutely.** 17.6.3 stands
unchanged: "Tools reference the abstraction, not the provider. When a provider
is substituted, the abstraction remains constant." An abstraction that named a
provider would still violate `17` rule 21, and the test asserting so
(`test_an_abstraction_may_not_name_its_provider`) remains in force.

**Governance artifacts remain provider-neutral.** A policy, ruling or amendment
may not name a technology. `15.6.3`'s screen is unaffected.

**Integration manifests, deployment manifests and implementation work may name
providers and technologies**, because that is what an Implementation
Specification is for. The portability guarantee of 17.23 is preserved by the
abstraction layer above the manifest, not by pretending the manifest has no
provider.

### Why this reading rather than the others

It is the only reading under which the whole corpus is simultaneously true.
Grandfathering `03` leaves the conflict live for the next technology decision.
Declaring the conflict genuine requires amending a ratified document, which is
a heavier act than interpretation and one 15.19.2 reserves for cases where
interpretation cannot resolve the text. Treating the prohibition as absolute
would make the system unimplementable, since every implementation names
something.

The distinction this ruling draws — **abstractions and governance are neutral;
implementation is specified** — is the distinction `17.6.3` already relies on.
The ruling makes explicit what the portability model presupposes.

## Consequences

**Unblocked for construction:**

- `integration_registry`, `integration_gateway`
- `deployment_registry`, `deployment_gateway`
- `evolution_gateway`

**Reinstated:** the 35 rules in `03` that mandate specific technologies are
constitutional and binding on implementation work. They move from *blocked* to
*binding*, and where this build does not satisfy them — it uses no FastAPI, no
PostgreSQL, no Temporal — that is now a **recorded deviation from a binding
rule**, not an unresolvable ambiguity. The deviation is scoped: this build is
in-process throughout, as every one of its 22 already-built modules is, and
adopting the named runtime stack is a deployment activity that CIR-001's
resolution permits but does not itself perform.

**Unchanged:** `17` rule 21, `18` rule 18 and `19` rule 22 remain non-violable
with respect to capability abstractions and governance artifacts. This ruling
scopes them; it does not weaken them.

## Standing

This is an interpretation under 15.19, not an amendment under 15.20. It is
binding on its scope and remains subordinate to the constitutional text
(15.19.1). If `03`, `17`, `18` or `19` is later amended to address the naming
question directly, this interpretation is superseded by that text.
