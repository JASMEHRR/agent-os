1. High-Level System Overview
1.1 Architectural Paradigm
Agent OS is a distributed, event-driven, multi-agent operating system built on a microservices foundation. It is not a monolithic application. It is not a single LLM with plugins. It is an orchestration layer that coordinates autonomous, specialized agents through durable workflows, with every subsystem designed for horizontal scalability, local-first operation, and production resilience.
The architecture adheres to Hexagonal Architecture (Ports and Adapters) at the service level and Event-Driven Architecture at the system level. No service holds business-critical state in memory. All inter-service communication occurs through the Event Bus or through the API Gateway. Direct service-to-service HTTP calls are prohibited except for health probes.

2.3 Technology Tradeoffs
Table
Decision	Rejected Alternative	Rationale
Temporal over Celery	Celery	Temporal provides durable workflow state, saga compensation, and visibility into long-running processes. Celery lacks workflow durability and complex retry semantics.
Redis Streams over Kafka	Apache Kafka	Redis is already required for caching and sessions. Streams provide sufficient durability and consumer groups without JVM operational overhead. Kafka is preferred only if event volume exceeds 100k/sec sustained.
Apache AGE over Neo4j	Neo4j	Keeps graph data in PostgreSQL, reducing operational complexity. If graph query complexity exceeds AGE capabilities, migration to dedicated graph DB is supported via the port-adapter pattern.
MinIO over cloud S3	AWS S3	MinIO runs locally and on-premise, satisfying Local First (3.1). Cloud S3 can be added as a replication target via MinIO bucket federation.
Docker Swarm default over K8s	Kubernetes default	Swarm satisfies production needs for single-node and small-cluster deployments with significantly lower operational complexity. K8s is supported but not required for initial deployment.
3. Complete Component Architecture
3.1 API Gateway
Responsibility: All external ingress. No external client communicates directly with any internal service.
Capabilities:
OAuth2/OIDC authentication with JWT validation
RBAC authorization (Casbin-backed)
Rate limiting per tenant, per user, per API key
Request/response transformation
API versioning (/v1/, /v2/)
Request ID generation and trace context injection
WebSocket support for real-time dashboard updates
OpenAPI schema serving
Interfaces:
Inbound: HTTP/1.1, HTTP/2, WebSocket
Outbound: HTTP/1.1 to internal services (via service discovery)
Events: Emits gateway.request_received, gateway.response_sent
Scaling: Stateless. Horizontally scalable behind a load balancer.
Design Rationale: Centralizes cross-cutting concerns. Prevents every service from reimplementing auth and rate limiting.
3.2 Agent Runtime
Responsibility: The execution environment for all agents. Agents are not long-running processes. They are stateless workers that wake up in response to workflow tasks.
Capabilities:
Agent worker pool management
State hydration from Memory Gateway before execution
Context assembly (relevant memories, tool schemas, workflow state)
Agent prompt rendering and LLM invocation via LLM Router
Tool call dispatch to Tool Executor
Result validation against output schema
Event emission upon completion/failure
Heartbeat reporting to Workflow Engine
Interfaces:
Inbound: Temporal activity tasks
Outbound: Memory Gateway (gRPC), LLM Router (HTTP), Tool Registry (HTTP), Event Bus (Redis Streams)
Scaling: Stateless workers. Scale horizontally based on Temporal task queue depth.
Design Rationale: Agents must not own their lifecycle. The Workflow Engine owns scheduling; the Runtime owns execution. This separation enables independent scaling and prevents agent state corruption from affecting orchestration.
3.3 Workflow Engine (Temporal)
Responsibility: Durable orchestration of all business processes. Every autonomous action flows through a workflow.
Capabilities:
Workflow definition as code (TypeScript or Python SDK)
Long-running process durability (survives worker restarts)
Saga pattern implementation for compensating transactions
Child workflow spawning for parallel agent execution
Timer and cron support for scheduled operations
Retry policies with exponential backoff
Workflow search and visibility UI
Event-driven workflow triggering (via Event Bus adapters)
Key Workflow Types:
Table
Workflow	Purpose	Typical Duration
BusinessDiscoveryWorkflow	Research → Idea generation → Ranking	30 min – 2 hours
ProductBuildWorkflow	Planning → Development → Testing → Deployment	2 hours – 2 days
MarketingCampaignWorkflow	Content creation → Scheduling → Publishing → Monitoring	1 hour – 1 week
ContinuousImprovementWorkflow	Analytics → Diagnosis → Prompt refinement → A/B test	1 hour – 1 day
Interfaces:
Inbound: Temporal gRPC, Event Bus triggers
Outbound: Temporal task queues to Agent Runtime
Scaling: Temporal server scales horizontally. Workers scale independently per task queue.
Design Rationale: Temporal was selected because autonomous business processes are long-running, failure-prone, and require exactly-once execution semantics. Celery cannot provide durable workflow state or saga compensation.
3.4 Event Bus
Responsibility: The nervous system of Agent OS. All significant state changes and commands flow through the Event Bus.
Capabilities:
Redis Streams with consumer groups
At-least-once delivery semantics
Schema validation on publish (via registry)
Dead-letter stream for failed deliveries
Event archival to MinIO for replay
Partitioning by event category (modulo stream key)
Backpressure via pending entry list monitoring
Event Categories:
Table
Category	Stream Key	Purpose
business	stream:business	Domain events (idea created, product launched)
agent	stream:agent	Agent lifecycle (started, completed, failed)
system	stream:system	Infrastructure (service up/down, scaling events)
command	stream:command	Imperative instructions (approve, cancel, retry)
audit	stream:audit	Security-relevant actions
Interfaces:
Inbound: Redis XADD from any service
Outbound: Redis XREADGROUP from consumer services
Scaling: Redis Cluster mode for horizontal partitioning. Consumer groups distribute load across service instances.
3.5 Memory Gateway
Responsibility: Unified access layer for all memory systems. No agent accesses Redis or PostgreSQL directly.
Capabilities:
Working memory read/write (Redis)
Long-term fact storage (PostgreSQL)
Semantic search (pgvector)
Knowledge graph queries (Apache AGE)
Cache management (TTL, invalidation)
Session state management
Memory tiering (hot → warm → cold migration)
Interfaces:
Inbound: gRPC (internal), HTTP (for debugging)
Outbound: PostgreSQL, Redis, MinIO (cold storage)

3.6 Tool Registry
Responsibility: Central catalog of all capabilities available to agents. Tools are not hardcoded into agents.
Capabilities:
Tool manifest storage (JSON Schema definitions)
Tool versioning and deprecation
Permission mapping (which agents can use which tools)
Tool discovery API (agents query at runtime)
Tool health monitoring
Tool usage analytics
Tool Manifest Schema:
Table
Field	Type	Description
tool_id	UUID	Unique identifier
name	string	Human-readable name
version	semver	Tool version
description	string	LLM-visible description
input_schema	JSON Schema	Validated input structure

sandbox_level	enum	none, container, gvisor, firecracker

Interfaces:
Inbound: HTTP REST, Event Bus (for health updates)
Outbound: Tool Executor (gRPC for execution requests)
3.7 Tool Executor
Responsibility: Sandboxed execution of tool code. The only component allowed to spawn arbitrary processes.
Capabilities:
Container lifecycle management (Docker/gVisor/Firecracker)
Network egress control (deny-by-default, allowlist)
Filesystem isolation (read-only root, explicit volume mounts)
Resource limits (CPU, memory, disk, network bandwidth)
Output capture and validation
Cleanup guarantee (containers are always destroyed)
Secret injection via mounted files (never env vars)
Sandbox Levels:
Table
Level	Isolation	Use Case
none	Python function call	Internal, deterministic utilities (math, formatting)
container	Docker container + network deny	Standard tools (web scraper, file processor)
gvisor	gVisor runsc + seccomp	Untrusted code, user-provided plugins
firecracker	MicroVM	Maximum isolation for security-critical operations
Interfaces:
Inbound: gRPC from Tool Registry
Outbound: Event Bus (execution results), MinIO (artifact storage)
3.8 LLM Router
Responsibility: All LLM traffic flows through this service. No agent calls an LLM directly.
Capabilities:
LiteLLM proxy for unified API
Model selection based on task complexity and cost budget
Local model management (Ollama/vLLM health, loading)
Cloud API fallback with circuit breakers
Prompt token counting and budget enforcement
Response caching (semantic cache via Redis + exact cache)
Cost tracking per request, per agent, per business
Structured output enforcement (JSON mode, function calling)
Context assembly from Memory Gateway
Model Tiers:
Table
Tier	Models	Use Case	Cost Priority
Nano	Local 3B-7B (Phi-3, Mistral 7B)	Routing, classification, filtering, simple extraction	Zero API cost
Standard	Local 13B-30B (Llama 3 70B, Mixtral 8x7B)	Standard tasks: summarization, drafting, code generation	Minimal API cost
Premium	Claude 3.5 Sonnet, GPT-4o	Complex reasoning, strategy, creative generation, error recovery	Cost justified by quality gap
Interfaces:
Inbound: HTTP (OpenAI-compatible API)
Outbound: Ollama (HTTP), vLLM (HTTP), Cloud APIs (HTTP), Memory Gateway (for context)
3.9 Cost Manager
Responsibility: Prevents runaway costs. Enforces the "Free API First" and "Cost Transparency" principles.
Capabilities:
Real-time cost tracking per operation, agent, business, tenant
Budget enforcement (hard stops and soft warnings)
Cost-based circuit breakers
Cost projection and alerting
Optimization recommendations (cache hit rates, model downgrading)
Integration with LLM Router for pre-flight budget checks
Budget Levels:
Table
Level	Action	Trigger
Green	Normal operation	Below 50% of budget
Yellow	Warning logged, alert sent	50-80% of budget
Orange	Model downgrading enforced	80-95% of budget
Red	Operations halted, human escalation	>95% of budget
Interfaces:
Inbound: HTTP (from LLM Router, Tool Executor), Event Bus
Outbound: Event Bus (alerts), Alertmanager (pages)
3.10 Plugin Manager
Responsibility: Extends Agent OS without modifying core code.
Capabilities:
Plugin manifest validation
Container image registry integration
Plugin sandbox deployment
Plugin lifecycle (install, enable, disable, uninstall)
Plugin API exposure through API Gateway
Plugin event subscription (plugins can listen to Event Bus)
Plugin Interface:
gRPC service with predefined interface
Manifest declaring: capabilities, event subscriptions, required permissions, resource limits
Plugins run as sidecars or separate containers, never in core process space
3.11 Monitoring & Observability
Responsibility: The system cannot be automated safely if it cannot be observed.
Capabilities:
Prometheus metrics exposition (/metrics)
Structured JSON logging via structlog
OpenTelemetry trace collection
Grafana dashboards for: system health, agent performance, business metrics, cost tracking
Alertmanager for SLO-based alerting
Loki for log aggregation and search
Tempo for distributed trace visualization
Critical Dashboards:
Table
Dashboard	Metrics
System Health	CPU, memory, disk, network, queue depths, error rates
Agent Performance	Success rate, latency, tool usage, LLM token consumption
Business Metrics	Revenue, MRR, churn, conversion rates per product
Cost Tracking	Spend per agent, per business, per model tier, budget burn rate
Security	Auth failures, permission denials, audit event volume
4. Multi-Agent Architecture
4.1 Agent Definition
An Agent in Agent OS is not a process. It is a deployable artifact consisting of:
Agent Manifest (manifest.yaml): Metadata, capabilities, permissions, autonomy level
Prompt Templates (prompts/): Jinja2 templates for LLM interaction
Tool Bindings (tools.yaml): Declared tool dependencies
Output Schemas (schemas/): Pydantic models for validation
Business Logic (src/): Python module with agent-specific deterministic functions
4.2 Agent Manifest Specification
yaml
# Architectural Specification — Not Implementation Code
agent:
  id: "agent-market-research-v1"
  name: "Market Research Agent"
  version: "1.2.0"
  autonomy_level: 2          # Level 1-4 per Human Approval Rules
  capabilities:
    - "business.opportunity.discover"
    - "business.competitor.analyze"
  required_tools:
    - "web-scraper"
    - "sentiment-analyzer"
  memory_access:
    read: ["market_data", "competitor_profiles"]
    write: ["research_reports", "opportunity_scores"]
  max_cost_per_operation: 0.50  # USD
  timeout_seconds: 300
  retry_policy:
    max_attempts: 3
    backoff: exponential

4.4 Agent Communication
Agents never communicate directly. All interaction is mediated by the Event Bus.
Pattern: Command → Event → Reaction
Agent A completes analysis, emits business.analysis.completed
Event Bus routes to consumers subscribed to business.*
Agent B (Idea Ranker) receives event, evaluates if it should act
Agent B emits business.idea.ranked or takes no action
This enforces loose coupling and enables event replay for debugging.
4.5 Agent Discovery
The Workflow Engine discovers agents by querying the Agent Registry (stored in PostgreSQL):
Table
Discovery Method	Use Case
Capability Match	"Find all agents that can handle business.content.generate"
Event Subscription	"Which agents are listening to business.product.launched?"
Direct Reference	Workflow explicitly names agent by ID
4.6 Agent Isolation
Table
Isolation Layer	Mechanism
Process	Each agent runs in a separate Temporal activity worker process
Network	Agents have no network access except through Tool Executor
Data	Agents access memory only through Memory Gateway with RBAC
Compute	Agent workers have CPU/memory limits via container constraints
Financial	Cost Manager enforces per-operation budgets
4.7 Agent Permissions
Agents use Service Account Identity. Each agent has a unique JWT identity with scoped claims:
JSON
{
  "sub": "agent-market-research-v1",
  "roles": ["agent:market-research"],
  "permissions": [
    "memory:read:market_data",
    "tool:use:web-scraper",
    "event:publish:business.*"
  ],
  "budget_limit": 0.50,
  "iat": 1722422400,
  "exp": 1722426000
}
Tokens are short-lived (1 hour max) and issued by the API Gateway's internal CA.
4.8 Agent Health Monitoring
Heartbeat: Agents report heartbeat to Workflow Engine every 30 seconds during execution
Stall Detection: No heartbeat for 2× timeout triggers automatic termination and retry
Success Rate Tracking: Prometheus metrics track per-agent success rates; sustained <90% triggers alert
Drift Detection: Agent output schemas are continuously validated; schema drift logs warning
4.9 Agent Recovery
Table
Failure Mode	Detection	Recovery Action
Agent Crash	Heartbeat timeout	Workflow Engine reschedules to new worker; state rehydrated from Memory Gateway
Agent Stall	Progress timeout	Activity times out; retry with exponential backoff
Agent Misbehavior	Output schema violation	Event emitted to system.agent.violation; human alert; agent quarantined
Agent Loop	Excessive tool calls (>50)	Hard limit enforced by Workflow Engine; workflow fails with diagnostic

Every event conforms to this schema:
Table
Field	Type	Description

schema_version	semver	Event schema version
event_type	string	Dot-notation category (e.g., business.idea.ranked)

metadata	JSON	Context: correlation IDs, causation IDs, user agent

Table

5.6 Dead-Letter Queue (DLQ)
Storage: Separate Redis Stream + MinIO archive
Retention: 30 days in Redis, indefinite in MinIO
Processing: Human-reviewed via dashboard. Replay capability via admin API.
Alerting: DLQ depth > 10 triggers P2 alert; > 100 triggers P1 page.
5.7 Event Replay
Events are archived to MinIO in Parquet format within 5 minutes of emission. Replay workflow:
Operator specifies time range and event filter
Temporal workflow reads archived events from MinIO
Events are re-injected into Event Bus with replay: true metadata
Consumers handle replay idempotently (via event_id deduplication)

8.2 Model Selection Logic
The Router uses a cascading decision tree:

Complex: Strategy, reasoning, error analysis → Premium tier
Availability Check: Circuit breaker status for each model endpoint
Fallback Chain: If primary model fails, try next in tier, then next tier
Cache Check: Semantic cache queried before inference

### 8.5 Prompt Pipeline 

| Stage | Description | Principle |
|-------|-------------|-----------|
| **1. Template Selection** | Jinja2 template chosen by agent based on task type | Tool Driven (3.6) |
| **2. Context Retrieval** | Relevant memories fetched from Memory Gateway via semantic + structured query | Memory First (3.4) |
| **3. Context Assembly** | Retrieved context ranked by relevance, truncated to fit token budget | Context Engineering (5.3) |
| **4. Input Sanitization** | External data scrubbed for prompt injection, HTML stripped, length validated | Input Sanitization (10.3) |
| **5. Prompt Rendering** | Jinja2 renders final prompt with context, instructions, and output schema | — |
| **6. Token Budget Check** | Pre-flight token count; if over budget, context is summarized or truncated | Cost Optimization (11) |
| **7. LLM Invocation** | Routed to appropriate model tier via selection logic | Model Agnosticism (5.1) |
| **8. Output Parsing** | Response parsed against Pydantic schema; invalid outputs trigger retry | Deterministic Boundaries (5.2) |
| **9. Grounding Validation** | Factual claims checked against source citations; hallucination flags raised | Hallucination Mitigation (5.4) |
| **10. Cache Storage** | Valid response stored in semantic cache for future retrieval | Aggressive Caching (11.3) |

### 8.6 Context Retrieval

The Memory Gateway provides context to the LLM Router through a **multi-modal retrieval pipeline:**

1. **Semantic Search:** Query embedding compared against `memory_embeddings` via pgvector HNSW index. Returns top-K relevant documents.
2. **Structured Query:** PostgreSQL queries fetch recent facts, decisions, and outcomes filtered by `tenant_id`, `agent_id`, and `fact_type`.
3. **Knowledge Graph Traversal:** Apache AGE Cypher queries traverse relationships (e.g., "find competitors of businesses in the same market as this idea").
4. **Session Hydration:** Redis provides active workflow state and recent conversation turns.
5. **Re-ranking:** A local cross-encoder model re-ranks retrieved documents by relevance to the specific query, improving precision over pure vector similarity.

**Context Budget Management:**
- Each agent declares a `max_context_tokens` in its manifest.
- The retrieval pipeline fills context from most to least relevant until 80% of budget is used.
- Remaining 20% is reserved for the LLM's response generation.
- If critical context exceeds budget, a summarization agent (Nano tier) compresses long documents.

### 8.7 Cost Optimization

The LLM Router integrates with the Cost Manager at three checkpoints:

| Checkpoint | Action |
|------------|--------|
| **Pre-flight** | Estimate tokens × model cost; reject if over agent budget |
| **Routing** | Prefer Nano → Standard → Premium only when justified |
| **Post-flight** | Record actual cost; update running totals; trigger alerts if thresholds breached |

**Caching Strategy:**
- **Exact Cache:** MD5 hash of (model + prompt + temperature) → stored in Redis. Hit rate target: >30%.
- **Semantic Cache:** Embedding of prompt queried against pgvector; similar prompts (cosine similarity >0.95) return cached response. Hit rate target: >15%.
- **Embedding Cache:** Frequently referenced documents have pre-computed embeddings stored in Redis to avoid re-embedding.

### 9.6 Tool Sandboxing

Every tool execution occurs within a **sandbox boundary** determined by its `sandbox_level`:

| Level | Isolation | Network | Filesystem | Use Case |
|-------|-----------|---------|------------|----------|
| `none` | Python function in agent worker process | Same as agent | Same as agent | Pure computation, no I/O (math, formatting) |
| `container` | Docker container | Denied by default; explicit allowlist | Read-only rootfs; tmpfs for writes | Web scraping, API calls, file processing |
| `gvisor` | gVisor runsc + seccomp | Denied by default; explicit allowlist | Overlay filesystem; no host access | User-provided plugins, untrusted code |
| `firecracker` | Firecracker microVM | Virtual NIC with egress filtering | Virtio block device; encrypted | Security-critical, financial operations |

**Sandbox Enforcement:**
- Container images are scanned by Trivy before registration
- Network policies (Cilium/Calico in K8s; Docker network policies in Swarm) enforce egress allowlists
- Seccomp profiles restrict syscalls
- Resource limits (cgroups) enforce CPU, memory, disk, and network bandwidth caps
- All sandboxes have a **kill switch**: exceeding timeout or resource limits triggers immediate SIGKILL

### 9.7 Tool Validation

Three validation layers:

1. **Input Validation:** Pydantic validates against `input_schema` before sandbox entry
2. **Output Validation:** Pydantic validates against `output_schema` after sandbox exit
3. **Semantic Validation:** For critical tools, a Nano-tier LLM verifies that the output is semantically coherent and safe (e.g., generated code does not contain obvious malware patterns)

## 10. Workflow Architecture

### 10.1 Workflow as Code

All business processes in Agent OS are **durable workflows** implemented in Temporal. A workflow is not a script; it is a stateful, fault-tolerant orchestration that survives worker restarts, network partitions, and database failures.

**Workflow Definition Structure:**

| Component | Responsibility |
|-----------|---------------|
| **Workflow Function** | Orchestration logic: sequencing, branching, parallel execution, timers |
| **Activities** | Individual units of work executed by Agent Runtime workers |
| **Saga Compensations** | Rollback logic for each mutating activity |
| **Signals** | External events that workflows can receive (approve, cancel, pause) |
| **Queries** | Read-only methods to inspect workflow state |

### 10.3 Planning Phase

Before execution, the Workflow Engine constructs an **Execution DAG (Directed Acyclic Graph):**

- **Nodes:** Activities (agent executions, tool calls, human approval gates)
- **Edges:** Dependencies (data flow, sequencing constraints)
- **Annotations:** Retry policies, timeouts, compensation activities, required autonomy levels

The DAG is validated for:
- Cycles (rejected)
- Missing agent registrations (rejected)
- Budget violations (rejected or downgraded)
- Permission conflicts (rejected)

### 10.4 Execution Phase

Activities are dispatched to Agent Runtime workers via Temporal task queues. Each activity:

1. Receives workflow context (read-only) + activity input
2. Hydrates agent state from Memory Gateway
3. Executes agent logic (LLM calls, tool calls)
4. Returns structured output to workflow
5. Workflow records result and proceeds to next node

**Parallel Execution:** Independent activities execute concurrently. The Workflow Engine manages synchronization barriers where activities must complete before downstream nodes begin.

### 10.5 Validation Phase

Before workflow completion:

| Validation Type | Executor | Failure Action |
|-----------------|----------|----------------|
| **Schema Validation** | Workflow Engine | Retry activity with corrected prompt |
| **Business Rule Check** | Deterministic function | Saga compensation + workflow failure |
| **Cost Audit** | Cost Manager | Alert if overrun; halt if critical |
| **Security Scan** | Tool Executor | Quarantine outputs, escalate |

### 10.6 Retry and Recovery

| Failure Type | Retry Strategy | Max Attempts | Escalation |
|--------------|---------------|------------|------------|
| Transient LLM error | Exponential backoff (1s, 2s, 4s, 8s) | 4 | Fallback model |
| Transient tool error | Fixed interval (5s) | 3 | Alternative tool |
| Schema validation failure | Immediate with corrected prompt | 2 | Human review |
| Budget exceeded | None | 0 | Human approval (Level 3) |
| Permission denied | None | 0 | Security alert + audit |
| Timeout | None (already at limit) | 0 | Saga compensation |

### 10.7 Reflection and Self-Improvement

Certain workflows include a **Reflection Activity** at the end:

1. Compare actual outcome to predicted outcome
2. Log deviation to `memory_decisions`
3. If deviation exceeds threshold, trigger `ContinuousImprovementWorkflow`
4. Improvement workflow may: refine agent prompts, update tool schemas, or recommend new tool development

### 10.8 Saga Compensation

For workflows that perform mutating operations (deployments, financial transactions, content publication), each activity has a **compensation activity:**

| Forward Activity | Compensation Activity |
|-----------------|----------------------|
| Deploy application | Rollback to previous version |
| Publish blog post | Unpublish / revert to draft |
| Spend ad budget | Request refund (if platform supports) |
| Create DNS record | Delete DNS record |

Compensations are executed in reverse order if any activity fails. If compensation fails, the workflow enters a **stalled** state requiring human intervention.

## 11. Security Architecture

### 11.1 Authentication

**Multi-Factor Identity:**

| Identity Type | Mechanism | Use Case |
|---------------|-----------|----------|
| **Human Users** | OAuth2/OIDC (Auth0/Keycloak) + MFA | Dashboard access, approval actions |
| **Service Accounts** | JWT signed by internal CA | Inter-service communication |
| **Agents** | Short-lived JWT (1-hour TTL) | Agent execution identity |
| **API Clients** | API Keys (SHA-256 hashed) | External integrations |

**Token Flow:**
```
Human/Client ──> API Gateway ──> OAuth2/OIDC Provider
                                    │
                                    ▼
                              JWT Issued
                                    │
                                    ▼
                              API Gateway validates
                              signature + claims
                                    │
                                    ▼
                              Request forwarded
                              with identity headers
                              (X-User-ID, X-Tenant-ID,
                               X-Roles)
```

### 11.2 Authorization

**RBAC + ABAC Hybrid Model:**

- **RBAC (Role-Based):** Broad permission groups (`admin`, `operator`, `agent-runner`, `viewer`)
- **ABAC (Attribute-Based):** Fine-grained access control using attributes:
  - `tenant_id`: Data isolation
  - `autonomy_level`: Maximum allowed autonomy
  - `budget_remaining`: Financial authorization
  - `time_of_day`: Some actions restricted to business hours

**Policy Enforcement Points (PEP):**
1. API Gateway (ingress)
2. Agent Runtime (before execution)
3. Tool Executor (before tool invocation)
4. Memory Gateway (before data access)

### 11.6 Encryption

| Layer | Mechanism | Key Management |
|-------|-----------|----------------|
| **Data at Rest (PostgreSQL)** | AES-256-GCM | PostgreSQL TDE or filesystem encryption |
| **Data at Rest (MinIO)** | AES-256-GCM | MinIO server-side encryption with Vault |
| **Data in Transit (Internal)** | mTLS (Linkerd or service mesh) | Internal CA, auto-rotation |
| **Data in Transit (External)** | TLS 1.3 | Let's Encrypt or commercial CA |
| **Application-Level** | Field-level encryption for PII | Vault Transit engine |

### 11.7 Permission Boundaries

**Agent Permission Boundaries** prevent privilege escalation:

- An agent with `tool:use:web_scraper` cannot grant itself `tool:use:deployment`
- Agents cannot request token scopes beyond their manifest declaration
- Workflow Engine enforces that child workflows inherit only the intersection of parent permissions and child requirements

## 12. Scalability Architecture

### 12.1 Scaling Dimensions

Agent OS scales across four dimensions:

| Dimension | Scaling Mechanism | Trigger |
|-----------|-------------------|---------|
| **Compute** | Horizontal pod/container scaling | CPU > 70% for 2 minutes |
| **Memory** | Redis Cluster expansion | Memory usage > 80% |
| **Storage** | PostgreSQL read replicas + partitioning | Query latency > 100ms p99 |
| **Agents** | Temporal worker pool expansion | Task queue depth > 100 |

### 12.2 From One Agent to Thousands

**Phase 1: Single Node (Development)**
```
┌─────────────────────────────────────┐
│  Single Machine                     │
│  ┌─────────┐ ┌─────────┐ ┌────────┐ │
│  │ FastAPI │ │ Temporal│ │ Redis  │ │
│  │ Gateway │ │ Server  │ │        │ │
│  └─────────┘ └─────────┘ └────────┘ │
│  ┌─────────┐ ┌─────────┐           │
│  │PostgreSQL│ │ Ollama  │           │
│  │+pgvector│ │         │           │
│  └─────────┘ └─────────┘           │
└─────────────────────────────────────┘
```

**Phase 2: Small Cluster (10-50 Agents)**
- API Gateway: 2 replicas behind Nginx
- Temporal: 2 frontend + 2 worker nodes
- PostgreSQL: Primary + 1 read replica
- Redis: Sentinel mode (3 nodes)
- Agent Runtime: 4-8 workers
- MinIO: 4-node distributed mode

**Phase 3: Production Cluster (100-500 Agents)**
- API Gateway: 4+ replicas with global rate limiting
- Temporal: 4 frontend + 8 worker nodes + separate visibility DB
- PostgreSQL: Primary + 2 read replicas, partitioned by tenant
- Redis: Cluster mode (6+ nodes)
- Agent Runtime: 20+ workers, sharded by capability
- MinIO: 8+ nodes, erasure coding
- Dedicated LLM inference nodes (GPU)

**Phase 4: Enterprise Scale (1000+ Agents)**
- Multi-region deployment
- Temporal with multi-cluster replication
- PostgreSQL Citus or sharding by tenant
- Redis Cluster per region with Cross-Region Replication
- Dedicated vLLM inference clusters with load balancing
- CDN for static assets

### 12.3 Queue-Based Load Leveling

```
┌─────────────┐     ┌─────────────┐     ┌─────────────┐     ┌─────────────┐
│   Burst     │────>│   Redis     │────>│   Temporal  │────>│   Agent     │
│   Traffic   │     │   Streams   │     │   Workers   │     │   Workers   │
│             │     │  (Buffer)   │     │  (Steady    │     │  (Process   │
│             │     │             │     │   drain)    │     │   rate)     │
└─────────────┘     └─────────────┘     └─────────────┘     └─────────────┘
```

Backpressure is implemented via:
- **Producer Throttling:** API Gateway returns 429 when queue depth exceeds threshold
- **Consumer Scaling:** Horizontal Pod Autoscaler (HPA) or Docker Swarm replicas
- **Shedding:** Non-critical events (analytics, non-urgent research) are dropped if system is overloaded

### 12.4 Database Scaling Strategy

| Technique | Application | Implementation |
|-----------|-------------|----------------|
| **Read Replicas** | Analytics queries, dashboard reads | PostgreSQL streaming replication |
| **Partitioning** | Large tables (`memory_embeddings`, `audit_log`) | PostgreSQL declarative partitioning by `tenant_id` + `created_at` |
| **Connection Pooling** | All services | PgBouncer in transaction mode |
| **CQRS** | Complex reporting | Materialized views refreshed by Celery/Temporal schedule |
| **Archival** | Old data | Parquet export to MinIO, soft-delete in PostgreSQL |

## 16. Failure Recovery

### 16.1 Agent Crash Recovery

**Detection:** Heartbeat timeout (2× activity timeout) detected by Temporal.

**Recovery Flow:**
```
1. Temporal marks activity as failed
2. Workflow checks retry count
   ├── If retries remain: Reschedule to new worker, rehydrate state from Memory Gateway
   └── If retries exhausted: Execute saga compensation, emit agent.execution.failed
3. Event Bus routes failure to Monitoring (alert) and Memory Gateway (log decision)
4. Human receives alert if autonomy level ≥ 2
```

**State Rehydration:** Agent state is never lost because:
- Working memory is in Redis (persistent)
- Long-term memory is in PostgreSQL (ACID)
- Workflow state is in Temporal (durable)

### 16.2 Queue Failure Recovery

**Scenario:** Redis Streams becomes unavailable.

**Recovery:**
1. Services buffer events in-memory with a 30-second TTL
2. If Redis recovers within TTL: Flush buffer
3. If Redis does not recover:
   - Critical events (approvals, deployments) are persisted to PostgreSQL fallback queue
   - Non-critical events (analytics, caching) are dropped
   - Alert triggered for human intervention
4. Upon recovery: PostgreSQL fallback queue is replayed into Redis Streams

### 16.3 Database Failure Recovery

**Scenario:** PostgreSQL primary is down.

**Recovery:**
1. Automatic failover to read replica (if configured with Patroni)
2. Services switch to read-only mode for non-critical operations
3. Critical writes (approvals, audit) are queued in Redis Streams
4. Human paged for manual failover decision
5. After recovery: Queued writes are replayed

**Backup Recovery:**
- Daily automated backups to MinIO
- Point-in-time recovery (PITR) via WAL archiving
- Monthly restoration drills

### 16.4 LLM Failure Recovery

**Scenario:** All LLM providers (local + cloud) are unavailable.

**Recovery:**
1. LLM Router circuit breakers open on all providers
2. Agent Runtime receives `LLMUnavailableError`
3. Workflow decision:
   - If task is non-critical: Defer to retry queue (Temporal timer for 1 hour)
   - If task is critical: Escalate to human (Level 4)
4. When any provider recovers: Circuit breaker half-opens, tests with health probe
5. Backlog processed in priority order

### 16.5 Tool Failure Recovery

**Scenario:** Tool execution fails (e.g., web scraper blocked by CAPTCHA).

**Recovery:**
1. Tool Executor returns structured error with failure category
2. Agent Runtime decides:
   - **Transient:** Retry with backoff (max 3 attempts)
   - **Permanent:** Try alternative tool (e.g., different scraper, or API fallback)
   - **Blocked:** Escalate to human with screenshot/context
3. If all alternatives fail: Workflow executes saga compensation for any completed steps

### 16.6 Network Failure Recovery

**Scenario:** Network partition between services.

**Recovery:**
1. Services detect partition via health checks
2. Partitioned services enter **degraded mode**:
   - API Gateway: Serve cached responses, queue writes
   - Agent Runtime: Pause new executions, complete in-flight activities
   - Memory Gateway: Serve from Redis cache, queue PostgreSQL writes
3. When partition heals: Reconcile queued operations
4. If partition lasts >5 minutes: Scale down affected services to prevent split-brain

### 16.7 Complete Failure Matrix

| Failure | Detection | Automatic Recovery | Human Escalation |
|---------|-----------|-------------------|------------------|
| Agent crash | Heartbeat timeout | Yes (retry + rehydrate) | After max retries |
| Agent stall | Progress timeout | Yes (timeout + retry) | After max retries |
| Queue failure | Redis health check | Yes (fallback queue) | If >5 min |
| DB primary failure | Connection timeout | Yes (failover if Patroni) | If failover fails |
| DB corruption | Checksum mismatch | No (restore from backup) | Immediate |
| LLM all-tiers down | Circuit breaker open | Partial (defer/cancel) | For critical tasks |
| Tool failure | Non-zero exit | Yes (retry/alternative) | After alternatives |
| Network partition | Health check failure | Partial (degraded mode) | If >5 min |
| Cost overrun | Budget threshold | Yes (halt + alert) | Immediate approval |
| Security breach | Audit anomaly | No (quarantine + alert) | Immediate |

## 17. Future Expansion

### 17.1 Plugin Architecture for Future Modules

The architecture is designed so that **future business domains** can be added without modifying core systems.

**Plugin Contract:**
```yaml
# Future plugin manifest example
plugin:
  id: "plugin-crypto-trading"
  version: "1.0.0"
  capabilities:
    - "business.trading.execute"
  event_subscriptions:
    - "business.market.opportunity"
  required_tools:
    - "exchange_api"
  sandbox: "firecracker"
  resources:
    cpu: "2"
    memory: "4Gi"
```

**Integration Points:**
- **Event Bus:** Plugins subscribe to existing streams
- **API Gateway:** Plugin endpoints are registered under `/plugins/{plugin_id}/`
- **Memory Gateway:** Plugins read/write to isolated memory namespaces
- **Tool Registry:** Plugins register their own tools
- **Agent Runtime:** Plugins may provide custom agent definitions

### 17.2 New Agent Onboarding

Adding a new agent requires zero core code changes:

1. Create directory in `agents/`
2. Write `manifest.yaml` with capabilities and permissions
3. Write prompt templates in `prompts/`
4. Write Pydantic schemas in `schemas/`
5. Register via Tool Registry API or CI pipeline
6. Workflow Engine discovers agent automatically via capability match

### 17.3 New Model Provider Onboarding

Adding a new LLM provider requires only LLM Router changes:

1. Add provider configuration to LiteLLM proxy
2. Define tier mapping (Nano/Standard/Premium)
3. Add circuit breaker configuration
4. Update cost estimates in Cost Manager
5. No changes to agents or workflows

### 17.4 Multi-Tenancy Expansion

Current architecture supports single-tenant deployment. Future multi-tenancy:

| Approach | Implementation | Impact on Core |
|----------|-----------------|----------------|
| **Namespace Isolation** | K8s namespace per tenant | None (already supported) |
| **Database Per Tenant** | Separate PostgreSQL DB per tenant | Minimal (connection routing) |
| **Row-Level Security** | PostgreSQL RLS policies | Minimal (middleware) |
| **Shared Schema** | `tenant_id` column on all tables | Already designed in |

### 17.5 Cross-Business Learning

Future enhancement: Agent OS operates multiple businesses and shares learnings:

- **Anonymized Memory Sharing:** Successful patterns from Business A are stored in a shared (anonymized) knowledge graph accessible to Business B
- **Model Fine-Tuning:** Aggregate agent interaction data is used to fine-tune local models for specific domains
- **Tool Marketplace:** High-quality tools developed for one business are published to the Tool Registry for others

### 17.6 Constitutional Amendment Process

When the architecture must evolve beyond current boundaries:

1. **Proposal:** Written ADR proposing architectural change
2. **Impact Analysis:** Document impact on all subsystems, agents, and workflows
3. **Review Period:** 7-day review by architecture team
4. **Prototype:** Change implemented in experimental namespace
5. **Chaos Test:** Verify no regression in staging
6. **Approval:** Human operator + Lead Architect sign-off
7. **Migration:** Gradual rollout via feature flags
8. **Documentation:** Update all architecture documents

## Appendix A: Non-Violable Architectural Rules

Derived from 01_PRINCIPLES.md, these architectural constraints are absolute:

1. **No Direct Service Calls:** All inter-service communication via Event Bus or API Gateway
2. **No Local State:** All business state externalized to PostgreSQL, Redis, or MinIO
3. **No Unregistered Tools:** All capabilities flow through Tool Registry
4. **No Raw LLM for Deterministic Logic:** Financial, security, and schema operations use deterministic code
5. **No Secrets in Code:** All credentials via Docker Secrets or Vault
6. **No Auto-Approve on Timeout:** Level 3+ actions require explicit human approval
7. **No Breaking Changes Without Migration:** Schema evolution requires backward compatibility
8. **No Production Without Tests:** CI enforces coverage and contract tests
9. **No Missing Observability:** Every service exposes /health, /ready, /metrics, and structured logs
10. **No Agent Over-Permission:** Agents receive minimum viable JWT scopes

## Appendix B: Glossary

| Term | Definition |
|------|------------|
| **Agent** | A deployable artifact (manifest + prompts + schemas + logic) executed by the Agent Runtime |
| **Activity** | A unit of work within a Temporal workflow, typically corresponding to one agent execution |
| **Autonomy Level** | The degree of independence an agent has (1-4), per Human Approval Rules |
| **Compensation** | A rollback action in a saga pattern that undoes a previously completed activity |
| **Event Bus** | The Redis Streams-based message backbone for all inter-service communication |
| **Memory Gateway** | The unified access layer for all data storage (hot, warm, cold, semantic, graph) |
| **Saga** | A sequence of transactions where each has a compensating transaction for rollback |
| **Sandbox** | An isolated execution environment for tools (container, gVisor, or Firecracker) |
| **Temporal** | The workflow engine providing durable execution and state management |
| **Tool** | A discrete capability with a defined input/output schema, executed in a sandbox |
| **Workflow** | A durable, orchestrated business process composed of activities and decisions |
